本仓库为单文件 HTML 高保真原型，未引入任何后端框架、错误码体系或结构化异常机制。错误处理完全由原生 JavaScript 的 `alert()` 完成，仅覆盖表单校验和简单业务约束场景。

1. 使用的系统/方式
- 无第三方错误库或全局错误处理器，全部使用浏览器内置 `alert()` 弹出提示。
- 通过条件判断在用户操作处直接拦截并提示，例如：
  - 附件上传时检查数量上限（最多 3 个）与文件大小（≤30MB），超限则 `alert('最多上传3个附件' / '文件"..."超过30MB限制')`。
  - 提交审批前校验申请理由非空、一级审批人必选，不满足则 `alert('未填写申请理由！' / '未选择一级审批人！')`。
- 页面状态展示采用颜色标签（如 `statusPill`、`sourceTag`）区分“已通过/审批中/草稿/已驳回/已撤回/已废弃”等状态，属于 UI 层面的错误/异常态呈现，而非程序异常。

2. 关键文件与位置
- `sales-forecast-prototype.html`：整个应用的唯一文件，包含所有样式、模板与脚本。错误处理逻辑集中在 `<script>` 段内：
  - `handleFiles(input)`：附件大小与数量校验。
  - `submitApproval()`：审批提交前的必填项校验。
  - `openModal/closeModal`、`openApproval/closeApproval`：弹窗打开/关闭时的基础输入校验入口。

3. 架构与约定
- 错误处理是“就地式”的：在事件回调函数内部直接做参数校验，失败即 `return` 并 `alert()`，没有统一的错误对象或错误码枚举。
- 所有提示文案以中文硬编码字符串形式出现，未抽象到常量或配置文件中。
- 页面状态流转（如“草稿→提交审批→审批中→已通过/已驳回/已撤回 | 已驳回/已撤回→废弃→已废弃”）通过 UI 标签与按钮禁用逻辑体现，但并未对非法状态转换进行运行时阻断。

4. 约定与约束
- 约束来源：代码中多处 `if(...){ alert(...); return; }` 模式表明以下规则被强制执行：
  - 附件数量不超过 3 个，单个文件不超过 30MB。
  - 提交审批必须填写申请理由且至少选择一个一级审批人。
- 约束范围：仅覆盖当前原型页面的前端交互校验；由于没有后端服务，不存在服务端错误码、异常传播或日志记录。
- 未发现 `try/catch`、`throw`、自定义 Error 类型、全局错误处理器或中间件等更高级的错误处理机制。

结论：该仓库作为纯前端静态原型，错误处理非常轻量，仅依赖 `alert()` 做客户端输入校验与提示，不具备企业级错误码、异常传播或统一错误处理架构。
